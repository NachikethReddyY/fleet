Agent Response Audit

Codex, Claude, OpenCode, and T3 history · configuration review · anonymized aggregate analysis

Your operating system for agents is unusually intentional. The largest remaining problem is not missing taste or safety policy; it is turning your repeated corrections into small, observable gates that an agent cannot quietly skip.

Verdict

Core finding. You give agents a high-quality product brief: outcome-first, iterative, evidence-conscious, and explicit about ownership. That produces strong direction. The failure mode is execution drift between those principles and the actual turn: agents can still substitute activity for proof, accept underspecified short follow-ups as authority, or treat a user correction as local feedback instead of a reusable regression rule.

Methodology and privacy boundary

Counts come from history tables and event files. The qualitative review looked for prompt shape, response behavior, task handoff, verification signals, and repeated instruction themes. It intentionally excludes raw prompts, source code, secrets, share URLs, account information, and personal details. “All” means all readable local records at the audit time, not every conversation that might exist in a remote service. Resumed sessions, sidechains, tool results, and duplicate projections were not treated as independent user tasks.

What you are doing right

In your prompts

  • You lead with an outcome. This lets an agent choose safe implementation details rather than asking you to orchestrate every command.
  • You iterate in small corrections. The very short follow-ups are often a strength: they preserve creative control when visual or behavioral taste is still being discovered.
  • You declare decision ownership. Product meaning, protected behavior, design direction, and external actions remain with you.
  • You ask for proof. Your guidance correctly distinguishes a passing technical check from the user-visible behavior that actually matters.
  • You use agents deliberately. Delegation is framed as a tool for independent, bounded work rather than a substitute for accountability.

In the shared guidance

  • Clear safety boundary. External actions are action-scoped and credentials are protected.
  • Strong learning contract. The learning seam and hint ladder make “teach me” materially different from “build it.”
  • Good UI standard. The browser is treated as evidence, not an optional polish pass.
  • Healthy anti-overbuild bias. The instructions value scope, local evidence, and the smallest complete solution.
  • Honest reporting norm. The required final summary asks for outcomes, evidence, and blockers rather than tool logs.

What weakens outcomes

Important nuance: these are workflow risks, not accusations that a short prompt is “bad.” Short iterative direction works well only when the model retains the active objective, current state, authority boundary, and the next acceptance check.

The productive but risky follow-up style

  • Compressed corrections can omit the protected behavior. A model may interpret “also,” “make it better,” or a visual adjustment as permission to reshape more of the product than intended.
  • Method requests can blur the deliverable. Asking for agents, research, plans, or a particular skill is useful, but the final artifact and proof need to stay first-class acceptance criteria.
  • Unbounded words invite unbounded exploration. “All details” is a good quality bar only when paired with a source boundary, privacy rule, and an honest limit on what evidence exists.

What a capable model still does poorly by default

  • Activity substitution: it can mistake commands, tests, research, or a polished explanation for evidence that the requested user outcome happened. One recorded workflow was marked completed while its own audit reported the expected artifact missing.
  • Local correction handling: it may acknowledge a correction without converting it into a durable constraint for the rest of the task.
  • Instruction collision: it can follow a standing process rule mechanically even when the current user scope says read-only or forbids supporting edits.
  • Fan-out and infrastructure blindness: a multi-agent workflow can fail through provider, gateway, auth, or context limits, yet still produce a superficially successful status unless every agent result is checked.
  • Completion language drift: it can say “done” before the artifact, browser behavior, external action, or acceptance test is independently established.

The governance gap

  • Policies are richer than the execution record. There is no shared per-task contract linking requested outcome → allowed changes → proof → final claim.
  • Corrections are not systematically harvested. The archive shows iterative work, but there is no formal rule for deciding whether a correction belongs in project guidance, a skill, or neither.
  • Metrics lack semantic context. Current records show turns and tools but not whether a task was superseded, accepted, abandoned, or visibly verified.

Recommended enforcement playbook

Do not make the guidance much longer. Add a short operating layer that forces the existing values to become observable behavior.

Minimal per-task contract

Before action: “Outcome: __. Allowed changes: __. Protected behavior: __. Proof: __. Stop when: __.” For simple questions, the contract collapses to “answer only; no edits.” This is short enough for normal work and resolves most ambiguity before it becomes rework.

Three changes worth making first

  1. Put the acceptance-evidence contract near the top of AGENTS.md. It reinforces your existing “done observably” rule with a concrete final-claim gate.
  2. Add the correction → regression loop to AGENTS.md. This converts your iterative product taste into a compounding system instead of repeating feedback each session.
  3. Add a publication-privacy check to html-communicator. Private-history reports should explicitly use aggregate/anonymized content and disclose their hosting/access posture before upload.
What not to add
  • Do not turn every task into a multi-page plan. The contract should take one or two lines unless risk is real.
  • Do not use more agents as a default response to uncertainty. The history and your own guidance correctly prefer narrow, independently checkable delegation.
  • Do not score agents by tool count, token count, or “completed” status alone. These are telemetry, not product evidence.

Limits and next measurement

Do not overread the scores. The databases preserve execution events, not a ground-truth label for whether you liked each answer, accepted a change, or whether later work superseded an interrupted turn. The next audit should measure a small tagged sample against explicit acceptance evidence.

After the three P0 changes, audit 20 new tasks with four fields: requested outcome, actual proof, user-visible check used, and whether a material correction recurred. That creates a real baseline for improvement without recording private prompt content.
